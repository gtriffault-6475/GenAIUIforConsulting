## Intent

**Problème :** `epic-2-retro-item-16` ("indicateur durable, pas seulement transitoire, d'une réponse agent échouée dans `ConversationHistory`", epic-2-retro-2026-09-16.md, marqué "décision de design nécessaire"). Aujourd'hui, un échec de réponse de l'agent (`sendMessage` retourne `assistantFailed:true`) n'apparaît que dans l'état React local `assistantError` de `Composer.tsx` -- perdu au premier changement de conversation, rechargement de page, ou fermeture d'onglet. Le message utilisateur, lui, reste bien persisté sans aucune réponse -- mais rien dans `ConversationHistory` (Server Component, lit uniquement MESSAGE) ne le signale : la conversation semble juste "en attente", indiscernable d'un message auquel le consultant n'a simplement pas encore eu de réponse.

**Approche :** Nouvelle colonne persistée sur MESSAGE, `assistantFailed` (booléen, uniquement sur les lignes `role:'user'`), posée explicitement par `actions/message.ts`'s `sendMessage` uniquement depuis son chemin d'échec réel -- jamais par le seed de fixtures (`actions/conversation.ts`), qui ne connaît aucune notion d'échec. `ConversationHistory.tsx` affiche un indicateur discret (texte muted + `role="alert"`, même motif que `Composer.tsx`'s `assistantError` existant) sous tout message utilisateur portant ce drapeau -- passif, aucune action de nouvelle tentative (hors périmètre, l'item ne demande qu'un indicateur).

**Décision (utilisateur, Checkpoint 1) :** Option A retenue -- colonne persistée, pas de dérivation. Confirmé au vu du faux positif vérifié qu'une dérivation pure produirait sur la conversation fixture "Cadrage de la note de mission".

## Boundaries & Constraints

**Always :** le drapeau ne doit jamais produire de faux positif sur la conversation fixture "Cadrage de la note de mission" (`FIXTURE_CONVERSATIONS`), qui se termine délibérément sur un message `user` sans réponse -- un choix de contenu démo assumé, pas un échec. Seul `sendMessage` pose le drapeau, explicitement, au moment de l'échec réel ; toute autre insertion (fixtures) le laisse absent/faux.

**Never :** pas de mécanisme de nouvelle tentative depuis ce ticket -- l'item ne demande qu'un indicateur visuel durable, pas une action corrective. `ConversationHistory` reste un Server Component en lecture seule (Story 2.1) -- aucune interactivité ajoutée.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Échec réel | `sendMessage` où `sendToAgent` échoue (pas de clé API, erreur réseau) | Le message utilisateur déjà persisté est marqué `assistantFailed:true` ; `ConversationHistory` l'affiche après rechargement, jours plus tard inclus | N/A |

## Implementation Notes

**Portée du marquage étendue aux 3 branches de retour `assistantFailed: true`.** Le Code Map ne pointait explicitement que la branche `agentResult.ok === false` (ligne ~256) comme site d'`UPDATE`. En implémentant, `sendMessage` s'est avéré avoir deux autres branches retournant `{ok:true, data:{assistantFailed:true, ...}}` sur le même message utilisateur déjà persisté : l'échec de `listLoadedSkillInstructions` et le `catch` englobant final ("agent call or reply persistence failed"). L'Intent du ticket ("un échec de réponse de l'agent... n'apparaît que dans l'état React local, perdu au premier changement de conversation") s'applique identiquement aux trois -- un helper local `markAssistantFailed()` (fermé sur `userMessageId`, capturé dans une variable dès l'insertion) est donc appelé dans les trois branches plutôt que la seule explicitement citée, pour que l'indicateur durable ne soit jamais moins complet que l'indicateur transitoire déjà affiché par `Composer.tsx`. Aucune AC ni Boundary n'est en tension avec cette extension -- toutes restent des échecs réels de `sendMessage`, jamais du seed de fixtures.

`markAssistantFailed()` encapsule son propre `try/catch` : si l'`UPDATE` lui-même échoue, seule l'erreur est loggée -- la réponse `ActionResult` déjà construite (avec `assistantFailed:true` transitoire, affiché une fois par `Composer.tsx`) part quand même, sans jamais transformer un échec d'écriture secondaire en `{ok:false}` sur `sendMessage`.

**Tour 2 (re-dérivation post spec-change, findings #1-4/#7/#9).** Code entièrement régénéré depuis le `baseline_commit` (le tour 1 avait été intégralement `git checkout`é) sur la base du Code Map amendé ci-dessus. Le motif `markAssistantFailed()`/`userMessageId` du tour 1 (KEEP) est conservé à l'identique dans sa structure -- seule sa signature change (`errorText: string` en paramètre, écrit dans `assistantErrorText` au même `UPDATE` que `assistantFailed`) et son corps gagne la vérification `result.changes === 0` (loggée, jamais levée), même motif que `actions/suggestion.ts`'s `reworkSuggestion` (`revert.changes === 0`/`applied.changes === 0`) cité par le Code Map. Les 3 sites d'appel passent chacun le texte déjà disponible localement dans leur branche (`loadedSkillsResult.error`, `agentResult.error`, la constante du `catch` externe -- extraite dans une variable `errorText` pour être à la fois retournée au client et passée à `markAssistantFailed`, un seul littéral au lieu de deux copies qui auraient pu diverger). Les 4 commentaires touchés citent `epic-2-retro-item-16` dès cette re-dérivation (pas `item-14`, l'erreur relevée par l'orchestrateur au tour 1). `components/ConversationHistory.tsx` : `role="status"` et `{msg.assistantErrorText ?? "L'agent n'a pas pu répondre à ce message."}` comme expression JS, jamais de `&apos;` JSX brut.
