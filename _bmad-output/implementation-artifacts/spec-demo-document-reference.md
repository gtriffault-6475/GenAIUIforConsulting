## Intent

**Problème :** point mis de côté dans `deferred-work.md` lors de la spec initiale du mode démo scripté (pour rester dans le budget de tokens) : rien ne suggère visuellement que l'agent s'appuie sur du contexte réel du projet au moment où il "rédige" le livrable RFP.

**Approche :** `actions/message.ts`'s `executeTool` (le point d'accroche déjà identifié par `deferred-work.md`), juste après un `createLivrableWithSuggestions`/`updateLivrableWithSuggestions` réussi sur l'entrée de création RFP du script démo, insère un document de référence dans DOCUMENT (`actions/document.ts`, nouvelle fonction `seedDemoReferenceDocument`, AD-2 inchangé -- reste le seul fichier autorisé à écrire DOCUMENT) si le mode démo est actif (`actions/demo.ts`'s `getDemoModeActive`, le mécanisme réel depuis le bouton bascule). `source: 'manual'` (jamais `'drive'`, AD-1 -- ce n'est pas une donnée Octopod) ; insertion idempotente sur un id fixe, pour ne jamais dupliquer si le tool-call se redéclenche (ex. la révision globale, même point d'accroche).

## Boundaries & Constraints

**Always :** le document n'apparaît que via ce point d'accroche unique (`executeTool`), jamais lors de la réinitialisation avant-vente ni ailleurs. Insertion idempotente (un id fixe, vérifié avant insertion) -- un second déclenchement (révision globale comprise, même `executeTool`) ne doit jamais créer de doublon.

**Never :** aucune lecture réelle du contenu du document par l'agent (hors périmètre, aucune fonctionnalité actuelle ne le fait). Aucun changement à `createLivrableWithSuggestions`/`updateLivrableWithSuggestions` eux-mêmes.

## Implementation Notes

Implémenté conformément à l'Intent gelé. `actions/document.ts` : nouvelle fonction `seedDemoReferenceDocument(projectId)` -- id dérivé par projet (`doc-demo-references-<projectId>`, jamais un id fixe partagé : `document.id` est la clé primaire globale de cette table, et le tool-call démo n'est pas scopé par `projectId`, voir commentaire dédié), vérifie l'existence avant insertion, `source: 'manual'`. `actions/message.ts` : `executeTool` appelle un nouvel helper local `seedDemoReferenceDocumentIfDemoActive()` juste après chacune des deux branches réussies (création et révision du livrable), qui relit lui-même `getDemoModeActive()` avant d'agir.

Deux bugs auto-détectés et corrigés avant toute revue : (1) `seedDemoReferenceDocument` écrite d'abord comme une fonction synchrone (`function ... : void`, `.all()`/pas d'`await`) -- `next build --turbopack` a échoué avec "Server Actions must be async functions" (ce fichier porte `'use server'`) ; corrigée en `async function ... : Promise<void>` avec `await db.select(...)`. (2) l'id de départ était une constante unique partagée entre tous les projets -- puisque le tool-call démo peut en théorie se déclencher sur n'importe quel projet (`matchDemoChatEntry` n'est jamais scopé par `projectId`), un second projet aurait trouvé l'id "déjà pris" et n'aurait jamais reçu sa propre copie ; corrigée par un id dérivé par projet (`demoReferenceDocumentId`).

Vérifié via deux scripts `tsx` jetables (sauvegarde/restauration du `db/local.db` réel, diff `.dump` complet confirmé identique après nettoyage) : 5/5 assertions (création idempotente, id distinct par projet), puis 3/3 (deux projets obtiennent chacun leur propre document, aucun partage). `npx tsc --noEmit`/`npx next build --turbopack` propres.

**Revue (bmad-review, blind-hunter) -- voir Review Triage Log.** Deux corrections réelles notables, toutes deux sur la même fonction : (1) `seedDemoReferenceDocument` n'avait aucun `try/catch` -- une exception (ex. une violation de contrainte `UNIQUE` sur une course entre deux déclenchements concurrents du même tool-call) remontait telle quelle à travers `executeTool` jusqu'au `try/catch` de `sendToAgent`, transformant un livrable déjà créé avec succès en `assistantFailed: true` -- l'inverse exact de la discipline "jamais laisser un écriture secondaire transformer un succès en échec" que ce même fichier documente déjà pour `markAssistantFailed`. Corrigé par un `try/catch` local (log seul, ne relance jamais) combiné à `onConflictDoNothing({ target: document.id })` sur l'`INSERT`, qui rend la course elle-même inoffensive (plus de violation de contrainte à attraper). (2) `resetAvantVenteWorkflow` (`actions/demo.ts`) ne supprimait jamais ce document -- rejouer la démo sur le même projet le montrait dès le tout premier message, avant même que le tool-call RFP ne se redéclenche, défaisant l'intérêt même de la fonctionnalité. Corrigé par un nouvel appel `tx.delete(document)` dans la transaction existante du reset, sur un id résolu via une nouvelle Server Action `resolveDemoReferenceDocumentId` (`actions/document.ts`, seule propriétaire de DOCUMENT, AD-2) -- résolue avant l'ouverture de la transaction, celle-ci restant synchrone comme le reste de ce fichier. Une incohérence de commentaire (`actions/message.ts` décrivait l'id comme "fixe", contredisant le commentaire de `actions/document.ts` sur la même fonction) a aussi été corrigée.

Revérifié après ces correctifs : 8/8 assertions dédiées (création idempotente y compris sous rappels répétés, reset supprime bien le document, un second reset sans document ne plante pas, le document réapparaît après un nouveau cycle création → reset → recréation). `npx tsc --noEmit`/`npx next build --turbopack` propres. Note de transparence : ce script de vérification a été exécuté par erreur contre le vrai `db/local.db` (pas une copie) ; `resetAvantVenteWorkflow`, appelé pour de vrai pendant le test, a effacé l'historique réel de conversations/messages/suggestions accumulé sur `proj-acme-rfp`. Restauré immédiatement depuis la sauvegarde prise avant le script, diff `.dump` complet confirmé byte-identique après restauration -- aucune perte.
