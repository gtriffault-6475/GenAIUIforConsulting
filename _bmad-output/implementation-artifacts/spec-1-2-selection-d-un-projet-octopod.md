## Intent

**Problem:** The scaffold from Story 1.1 has no data layer or entry point: a consultant cannot connect to any project, so nothing else (skills, conversations, panels, livrables) has anything to attach to.

**Approach:** Add the `PROJECT`/`APP_STATE` tables, a `ProjectProvider` port with a mock adapter seeding two example projects (one per use case), a Server Action to select a project, and a minimal UI — a project selector when none is active, a top bar naming the active project once one is — wired through the Ports & Adapters boundary so a real Octopod integration can replace the mock later without touching callers.

## Boundaries & Constraints

**Always:** `PROJECT` and `APP_STATE` are the only tables added to `db/schema.ts` this story; `APP_STATE` is a true singleton row (fixed id, upserted, never a second row); `actions/project.ts` is the only code that reads or writes `PROJECT`/`APP_STATE`; `ProjectProvider` is defined in `integrations/ports/` and implemented in `integrations/mock/`, wired at a single `integrations/index.ts` — `actions/` never imports `integrations/mock/` directly; the project selector opens through the existing `OverlayProvider` (AD-8), never its own `isOpen` state; selecting a project is the only way `activeProjectId` changes — no project is auto-selected on first load, an explicit empty/selector state shows instead.

**Never:** no Contexte/Livrables/Mattermost panels (Stories 1.3–1.5) or conversation surface (Epic 2) rendered yet — the page after selecting a project is a minimal top bar only; the mock `ProjectProvider` is the only implementation, no real Octopod call and no `integrations/real/*`; no create/edit/delete of a project from the UI — the list is fixed seed data in the mock adapter; do not pre-build `CONVERSATION`, `DOCUMENT`, or other later tables — only what this story needs.

**Acceptance Criteria:**
- Given no active project, when the app loads, then the project selector is shown and no other surface (conversation, skills, livrable) renders
- Given the project selector open, when a project is chosen, then it becomes the active project (persisted in `APP_STATE`) and the page renders a top bar naming it
- Given an active project, when the app is reloaded, then the same project remains active — selection persists rather than resetting
- Given an active project, when its data is inspected, then `octopodProjectRef` and `mattermostChannelRef` are already populated — no separate configuration step was required

## Implementation Notes

- `drizzle-orm/node-sqlite`'s query layer (every `db.select()`/`db.insert()`, not just its migrator) calls `stmt.setReturnArrays(...)` on the underlying `node:sqlite` prepared statement. That method does not exist on Node 23.11.0's `node:sqlite` `StatementSync` (confirmed by inspecting the prototype directly) — every drizzle query throws `TypeError: stmt.setReturnArrays is not a function` on that runtime. It does exist on Node 24.21.0 (installed via `brew install node@24`, kept keg-only, not linked as the system `node`, specifically to verify this story against the architecture spine's pinned Node 24 LTS without disturbing the machine's default `node`). This confirms Story 1.1's already-logged local-environment gap (dev machine on Node 23.11.0, spine pins 24 LTS) is not just cosmetic: on the wrong runtime, this story's Server Actions fail on every request. No code change was made for this — it isn't this story's or this repo's bug — but it gated verification and is worth flagging loudly for whoever next hits an unexplained `setReturnArrays` error.
- Because of the above, `db/client.ts` bootstraps the schema with a small bespoke migration runner (raw `sqlite.exec()`/`sqlite.prepare()` over the `db/migrations/<name>/migration.sql` files generated by `npm run db:generate`, tracked in a `__schema_migrations` table) instead of calling `drizzle-orm/node-sqlite/migrator`'s `migrate()`. That helper hits the same `setReturnArrays` call during its own bookkeeping query, so it cannot run on this local Node version either — but the chosen alternative was also the right call independent of that bug: it means a fresh clone or a deleted `db/local.db` self-heals on the next `npm run dev`/`next build`/`next start`, with no manual `db:push` step, satisfying the manual verification's "fresh `db/local.db`" check without adding an undocumented setup step. The next story that adds tables should extend this the same way: change `db/schema.ts`, run `npm run db:generate`, commit the new `db/migrations/<name>/` folder — no other wiring needed.
- `app/page.tsx` reads `APP_STATE` (mutated by `selectProject`) on every request, so it needs `export const dynamic = 'force-dynamic'` — without it, `next build` prerenders `/` to a static HTML shell from whatever `APP_STATE` held at build time (verified: omitting the export produced a `○ /` (Static) route in the build output; adding it produced `ƒ /` (Dynamic)). Static caching here would mean a reload after selecting a project could still show the empty-state selector in `next start` production mode, even though `npm run dev` (used by the spec's own manual-check instructions) would still look correct since dev never statically caches — so this would have been an easy production-only regression to miss.
- `app/globals.css` had no `.card`/`.button-primary`/`.nav-row`/`.nav-row-active` component classes yet (Story 1.1 only shipped the token custom properties and typography utility classes) — added them here, reading `DESIGN.md > Components` for the exact background/radius/typography pairing per component, all sourced from the existing CSS custom properties (no hardcoded colors). Later stories reuse these rather than re-defining them.
- Removed the `.gitkeep` placeholders in `actions/`, `integrations/ports/`, `integrations/mock/`, and `db/migrations/` now that each holds real files.
- Verified independently: `npx tsc --noEmit` and `npx next build --turbopack` both clean under Node 24.21.0; a live `npm run dev` session (Node 24) walked the full manual-check script — fresh `db/local.db` shows only the selector with both seed projects and no other surface, choosing "Réponse RFP — Acme Corp" swaps in a top bar reading "Réponse RFP — Acme Corp", and a hard reload keeps that same project active. Direct SQLite inspection after selection confirmed the `project` row carries populated `octopod_project_ref`/`mattermost_channel_ref` and `app_state` has exactly one row (`id = 'singleton'`) pointing at it.
- **Orchestrator note (independent re-verification, outside the implementation subagent's own pass):** the implementation subagent correctly diagnosed the Node 23/24 `setReturnArrays` gap but left it unresolved on the user's actual machine (installed Node 24 via `brew install node@24`, deliberately keg-only/unlinked "to avoid disturbing the machine's default `node`") and marked this story `done` regardless — meaning the feature it just built did not actually work for the user as the repository stood. Independently reproduced the failure against the machine's real default Node 23.11.0 (`getActiveProject failed ... TypeError: stmt.setReturnArrays is not a function`, confirmed live via `npm run dev`) before touching anything. Resolved properly, with the user's explicit choice of approach: installed `nvm` via Homebrew, added the required lines to `~/.zshrc`, ran `nvm install` in the repo (picks up `.nvmrc`'s `24`), and removed the now-redundant `brew node@24` keg. Re-ran the full manual verification end-to-end under `node v24.21.0` resolved via `nvm` — selector → selection → persistence-across-reload all confirmed working live in a browser. The spec was reverted from `done` back to `in-review` for this reason before re-closing it.

## Review Triage Log

- **`app/page.tsx` collapses a real `getActiveProject()`/`listProjects()` failure into the same rendering as "no project yet"** (verification-gap, blind-hunter, edge-case-hunter — 3 findings grouped, same root cause) — verdict `medium`, route `patch`. Verified by tracing: `actions/project.ts`'s catch blocks return `{ ok: false, error }` on any thrown error, and `page.tsx` only ever read `.data`, never checked `.ok`, so a transient DB read error after a project was already durably selected would silently re-render the empty-state selector — contradicting this story's own "selection persists" acceptance criterion in that specific failure mode, with no error shown or logged anywhere. Fixed: `page.tsx` now renders a distinct error message when either action returns `ok: false`, instead of falling through to the selector; `ProjectSelector` also shows a message when the resolved project list is empty.
- **All three Server Action catch blocks in `actions/project.ts` discard the thrown error with no logging** (blind-hunter, verification-gap) — verdict `medium`, route `patch`. Verified: `catch {}` in `listProjects`, `getActiveProject`, `selectProject` returns only a generic French string, so a real DB or provider failure is unobservable in server logs. Fixed: each catch now logs the underlying error via `console.error` before returning the generic message.
- **`selectProject`'s `project` upsert and `app_state` upsert run as two independent, non-transactional inserts** (blind-hunter, edge-case-hunter) — verdict `medium`, route `patch`. Verified: if the second insert throws, the first is already committed, leaving a persisted `project` row `app_state` never points at; two overlapping calls could also interleave. Fixed: both inserts now run inside one `db.transaction(...)`.
- **`app_state.active_project_id` declares a FK to `project.id` but nothing enables enforcement** (blind-hunter, edge-case-hunter — 2 findings grouped, same root cause) — verdict `false`. Verified directly (`node -e` against both a fresh `:memory:` connection and this story's own `db/local.db`): `node:sqlite`'s `DatabaseSync`, unlike the raw SQLite C library, enables `PRAGMA foreign_keys` by default — the reviewers' claim was based on the C-library default, which does not hold for this driver. Enforcement was already on. Kept an explicit `sqlite.exec('PRAGMA foreign_keys = ON')` in `db/client.ts` anyway, purely as self-documentation of an invariant this schema relies on, rather than leaving it implicit in a runtime default a future Node version could change — not a functional fix.
- **Clicking the selector's own toggle button while its dropdown is open reopens it instead of closing it** (edge-case-hunter) — verdict `medium`, route `patch`. Verified by dispatching the real `pointerdown` → `click` event pair against the live DOM: `OverlayProvider`'s outside-pointerdown handler saw the trigger button as "outside" `contentRef` (attached only to the dropdown panel) and closed the overlay on `pointerdown`; the subsequent `click` on the same button then read the now-closed state and reopened it — so the button can open the dropdown but visually can never close it by itself (Escape or an actual outside click still work). Fixed: `contentRef` now attaches to the wrapper `div` containing both the trigger button and the dropdown, so a click on the trigger no longer registers as "outside."
- **Migration runner in `db/client.ts` computes the pending-migrations list before opening its transaction, with no protection if a second OS process runs the same `CREATE TABLE` concurrently against a still-unmigrated `db/local.db`** (edge-case-hunter) — verdict `low`, route `patch`. Could not reproduce empirically (3 repeated fresh `next build` runs and a fresh `next dev` start against an unmigrated `db/local.db`, Node 24, all applied cleanly — this app's single dynamic route does not appear to trigger genuinely concurrent cold imports of `db/client.ts` from Turbopack's worker pool today), but the code has no actual guard against it, and later stories adding more routes/tables widen the window. Cheap insurance, same spirit as Story 1.1's nested-`OverlayProvider` guard: fixed by treating a "table already exists" error during migration application as "already applied by a concurrent process" (mark it applied, continue) instead of crashing that process.
- **Dropdown markup nests `role="option"` buttons inside plain `<li>` elements directly under `role="listbox"`** (blind-hunter) — verdict `low`, route `patch`. Verified against the ARIA listbox pattern: an `<li>` with no role breaks the listbox's required parent/child relationship to its options, which can make assistive tech misreport the list. Fix is a one-attribute addition (`role="presentation"` on each `<li>`), which is a direct correction despite the low severity, so it survives the "reject low+non-trivial-fix" rule. Fixed.
- **No automated tests were added** (blind-hunter) — rejected, out of scope. The architecture spine (this story's own loaded context) explicitly defers this project-wide: `## Deferred > "Tests automatisés, CI — non abordés"`, and Story 1.1 already established no test runner is installed. This is an intent-level exclusion, not a gap in this story's spec.
- **No focus management around the overlay (focus not moved into the dropdown, not returned to the trigger on close)** (blind-hunter) — rejected, `low`, precedent. Story 1.1's own triage already rejected the identical concern for `OverlayProvider` itself ("round 1's known, sighted, mouse-using test group is unlikely to hit it"). This story only reuses that mechanism and adds no new overlay-focus scope.
- **Migration runner splits `migration.sql` on the literal string `--> statement-breakpoint`, with no escaping** (blind-hunter) — verdict `false`. Verified against `drizzle-orm/migrator.js`'s own `readMigrationFiles`: it uses the identical `query.split("--> statement-breakpoint")`. This is drizzle-kit's own documented statement-boundary marker between generated migration statements, not incidental SQL content — the same convention the upstream library relies on.
- **Generated `db/migrations/.../snapshot.json` is missing a trailing newline** (blind-hunter) — rejected, `false`. This file is drizzle-kit's own generated output (`npm run db:generate`), not hand-authored; re-generating produces the same artifact.
- **No UI affordance to switch to a different project once one is active** (blind-hunter) — verdict `low`, route `defer`. Real gap a consultant would hit in daily use, but excluded by this story's own frozen Intent (only describes a selector when none is active and a top bar once one is) and by the epic's "un seul projet actif à la fois" framing with no switcher UX specified anywhere in round 1's planning artifacts — not a spec omission, a round-1 scope line. Logged to `deferred-work.md`.
